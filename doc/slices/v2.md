# VS-02 — Admin Authentication

**Project:** Photography Showcase Platform
**Vertical Slice:** VS-02 of 17
**Module:** Admin Authentication
**Objective:** Build a secure authentication system that allows only authorized photographers/admins to access the CMS.

> **VS-02 starts from the foundation created in VS-01.** At the end of this slice, the photographer should be able to securely log in, access the protected Admin Panel, refresh the page without losing authentication, and log out.

---

# 3. Authentication Strategy

For the initial product, use:

**Email + Password authentication**

Recommended architecture:

```text
Admin
 ↓
Login Form
 ↓
POST /api/v1/auth/login
 ↓
Backend Validation
 ↓
Find Admin
 ↓
Verify Password
 ↓
Generate Secure Session/Token
 ↓
Authenticated Admin
```

For production, prefer a **secure, HTTP-only cookie-based session/token approach** rather than storing long-lived authentication tokens in `localStorage`.

---

# 4. Admin Entity

The authentication system requires an `admins` table.

### Database structure

```text
admins
────────────────────────
id
name
email
password_hash
is_active
last_login_at
created_at
updated_at
```

### Fields

| Field         | Type      | Required |
| ------------- | --------- | -------- |
| id            | UUID      | Yes      |
| name          | VARCHAR   | Yes      |
| email         | VARCHAR   | Yes      |
| password_hash | TEXT      | Yes      |
| is_active     | BOOLEAN   | Yes      |
| last_login_at | TIMESTAMP | No       |
| created_at    | TIMESTAMP | Yes      |
| updated_at    | TIMESTAMP | Yes      |

---

# 5. Database Constraints

### Email

Must be unique.

```text
UNIQUE(email)
```

### Active status

Default:

```text
is_active = true
```

### Password

Never store:

```text
password
```

Store only:

```text
password_hash
```

---

# 6. Password Security

Use a secure password hashing algorithm such as:

**Argon2id** or **bcrypt**.

Recommended:

```text
Plain Password
      ↓
Password Hashing
      ↓
password_hash
      ↓
Database
```

Never:

* Store plain passwords
* Return password hashes through APIs
* Log passwords
* Send passwords back to frontend

# 10. Login API

### Endpoint

```text
POST /api/v1/auth/login
```

### Request

```json
{
  "email": "photographer@example.com",
  "password": "********"
}
```

### Success

```json
{
  "success": true,
  "data": {
    "admin": {
      "id": "uuid",
      "name": "Alex Photography",
      "email": "photographer@example.com"
    }
  }
}
```

Authentication state should be established securely.

Do **not** return:

```text
password
password_hash
```

---

# 11. Failed Login

For incorrect credentials, return a generic message such as:

> **Invalid email or password.**

Don't reveal whether:

* Email exists
* Email doesn't exist
* Account is inactive

This reduces account enumeration risk.

---

# 12. Inactive Admin

If:

```text
is_active = false
```

the admin cannot log in.

The public-facing response should remain generic rather than exposing account state.

Internally, the backend can distinguish the reason.

# 17. Unauthorized Response

If an unauthenticated user accesses a protected API:

```json
{
  "success": false,
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Authentication required"
  }
}
```

HTTP:

```text
401 Unauthorized
```

---

# 18. Forbidden Response

Authentication and authorization are different.

If a future user is authenticated but doesn't have permission:

```text
403 Forbidden
```

V1 has only one admin role, but the architecture should leave room for future role-based access control.

# 30. Password Requirements

Recommended minimum:

* 8+ characters

For a commercial product, a stronger password policy is preferable.

At minimum, reject obviously weak passwords such as:

```text
12345678
password
password123
```

during admin creation.

Don't impose arbitrary complexity requirements that encourage poor password practices unless there's a specific security reason.

---

# 31. Rate Limiting

Login endpoint should have rate limiting.

Example concept:

```text
Repeated failed login attempts
          ↓
Rate limiter
          ↓
Temporary restriction
```

This protects against brute-force attempts.

The exact thresholds should be configurable.

# 38. Business Rules

### BR-AUTH-001

Only authenticated admins may access protected CMS routes.

### BR-AUTH-002

Only active admin accounts may authenticate.

### BR-AUTH-003

Passwords must never be stored in plain text.

### BR-AUTH-004

Password hashes must never be returned to frontend clients.

### BR-AUTH-005

Invalid login attempts must return generic authentication errors.

### BR-AUTH-006

Authentication state must survive page refresh while the session remains valid.

### BR-AUTH-007

Logout must invalidate the active authentication session.

### BR-AUTH-008

Expired sessions must force reauthentication.

### BR-AUTH-009

Public visitors must not gain CMS access.

### BR-AUTH-010

Admin registration is not publicly available in V1.

# 39. Edge Cases

### EC-01

Admin enters email with leading/trailing spaces.

**Expected:** Trim and normalize appropriately.

### EC-02

Admin enters uppercase email.

**Expected:** Email matching should be handled consistently.

### EC-03

Wrong password.

**Expected:** Generic authentication error.

### EC-04

Non-existent email.

**Expected:** Same generic authentication error.

### EC-05

Inactive account.

**Expected:** Authentication denied.

### EC-06

Session expires.

**Expected:** Redirect to login.

### EC-07

Admin manually visits `/admin/photos` while logged out.

**Expected:** Redirect to `/admin/login`.

### EC-08

Admin logs out and presses browser Back.

**Expected:** Protected content should not become accessible.

### EC-09

Backend unavailable during login.

**Expected:** User-friendly connection error.

### EC-10

Multiple login clicks.

**Expected:** Only one request should be submitted while loading.

# 42. UAT Scenarios

## UAT-01 — Successful Login

**Given:** Valid admin credentials exist.

**When:** Photographer enters credentials and clicks Sign In.

**Then:** Photographer should be authenticated and redirected to the Admin Dashboard.

---

## UAT-02 — Invalid Login

**Given:** Incorrect credentials.

**When:** Photographer attempts to sign in.

**Then:** Login should fail with a generic error message.

---

## UAT-03 — Protected Admin

**Given:** Visitor is not authenticated.

**When:** Visitor accesses `/admin`.

**Then:** Visitor should be redirected to `/admin/login`.

---

## UAT-04 — Persistent Authentication

**Given:** Photographer is authenticated.

**When:** Browser page is refreshed.

**Then:** Photographer should remain authenticated if the session is valid.

---

## UAT-05 — Logout

**Given:** Photographer is authenticated.

**When:** Photographer clicks Logout.

**Then:** Authentication should be invalidated and the photographer should return to the login page.

---

## UAT-06 — Session Expiration

**Given:** Photographer's authentication session has expired.

**When:** Photographer accesses a protected resource.

**Then:** They should be redirected to login.
