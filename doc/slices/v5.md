# VS-05 — Photo Management

**Project:** Photography Showcase Platform
**Vertical Slice:** VS-05 of 17
**Module:** Photo Management / Portfolio Media CMS
**Depends on:** VS-01 Foundation, VS-02 Admin Authentication, VS-03 Admin Dashboard, VS-04 Category Management

---

## 1. Slice Goal

VS-05 builds the photographer's **complete photo management system**.

The photographer should be able to:

* Upload photos
* View uploaded photos
* Edit photo information
* Assign categories
* Set featured photos
* Publish/unpublish photos
* Hide/show photos
* Reorder photos
* Replace photos
* Delete photos safely
* Search and filter photos
* Manage portfolio images from desktop and mobile

The final flow:

```text
                    ADMIN
                      │
                      ↓
                 Photo Manager
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
     Upload          Browse        Search
       │              │              │
       ↓              ↓              ↓
   Photo Details    Edit/Delete    Filters
       │
       ↓
    Category
       │
       ↓
   Publish / Hide
       │
       ↓
  Public Portfolio
```

---

# 2. Why VS-05 Is Important

This is one of the **core slices of the entire product**.

The photography website is ultimately selling the photographer's work.

Therefore, the photo CMS needs to feel:

> **Fast, visual, premium, simple, and professional.**

It should not feel like a generic admin CRUD table.

The photographer should be able to manage hundreds of photographs without frustration.

# 6. Why Store Image Metadata?

Don't store only:

```text
image_url
```

Store metadata such as:

```text
width
height
file_size
mime_type
```

because it helps with:

* Performance
* Image validation
* Responsive rendering
* Debugging
* Optimization
* Storage management

# 65. Performance Requirements

Photography websites are image-heavy, so performance must be considered from this slice.

Admin:

* Lazy-load image thumbnails
* Use optimized thumbnails
* Paginate
* Avoid loading originals into the grid
* Use responsive image sizes
* Don't render hundreds of large images simultaneously

Public website later:

* Use optimized images
* Lazy loading
* Appropriate dimensions
* Responsive images
* CDN/storage optimization

* [ ] Admin authentication required.
* [ ] Validate all uploads server-side.

* [ ] Validate file size.

* [ ] Sanitize metadata.

* [ ] Prevent unauthorized photo modification.

# 67. Business Rules

### BR-PHOTO-001

Only authenticated admins can manage photos.

### BR-PHOTO-002

Every photo must have a valid category.

### BR-PHOTO-003

Category must be active when assigning a new photo.

### BR-PHOTO-004

Draft photos cannot appear publicly.

### BR-PHOTO-005

Hidden photos cannot appear publicly.

### BR-PHOTO-006

Hidden/inactive categories prevent associated photos from appearing publicly.

### BR-PHOTO-007

Photo slug must be unique.

### BR-PHOTO-008

Alt text is required.

### BR-PHOTO-009

Invalid image formats must be rejected.

### BR-PHOTO-010

Deleting a photo must clean up its storage assets.

### BR-PHOTO-011

Bulk operations must only affect selected photos.

### BR-PHOTO-012

Important photo actions create activity logs.

### BR-PHOTO-013

Photo ordering must persist.

### BR-PHOTO-014

Photo deletion must not affect unrelated photos.

---

# 68. Edge Cases

### EC-01 — Duplicate slug

Reject.

### EC-02 — Invalid category

Reject.

### EC-03 — Inactive category

Don't allow assigning to new photo.

### EC-04 — Upload failure

Allow retry.

### EC-05 — Partial batch failure

Keep successful uploads.

### EC-06 — Huge image

Reject if above configured limit.

### EC-07 — Unsupported file

Reject.

### EC-08 — Broken storage response

Don't save an incomplete photo record.

### EC-09 — Delete storage failure

Don't silently report complete deletion if assets remain.

### EC-10 — Delete photo used by another entity

Prevent or require appropriate handling.

### EC-11 — Empty search result

Show empty state.

### EC-12 — No photos

Show onboarding state.

### EC-13 — Session expiration during upload

Handle gracefully and avoid corrupt records.

### EC-14 — Duplicate upload

Optional future feature: detect duplicate files using checksum/hash.

This isn't mandatory for the first implementation, but it can make the product more premium.

Calculate a file hash:

```text
SHA-256
```

Store:

```text
file_hash
```

Then detect:

```text
Same image already exists.
```

This prevents accidental duplicate uploads.

For VS-05, **design for it but don't block the entire slice if you don't implement it initially.**
