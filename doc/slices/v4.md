# VS-04 — Category Management

**Project:** Photography Showcase Platform
**Vertical Slice:** VS-04 of 17
**Module:** Category Management
**Depends on:** VS-01 Foundation + VS-02 Authentication + VS-03 Dashboard

## 1. Slice Goal

VS-04 builds the complete **category management system** that allows the photographer to organize their photography work into meaningful categories.

The complete flow:

```text
Photographer
     ↓
Admin Dashboard
     ↓
Categories
     ↓
View Categories
     ├── Create
     ├── Edit
     ├── Delete
     ├── Activate / Deactivate
     ├── Reorder
     └── Manage Visibility
             ↓
       Used by Photos
       Used by Projects
             ↓
       Public Portfolio
```

The important architectural point is that categories created here will become the foundation for the **Photo Management, Project Management, and Public Portfolio** slices.

---

# 2. Why Category Management Comes Before Photos

The photographer shouldn't have to create categories while uploading every photo.

Instead:

```text
Category
   ↓
Wedding
   ↓
Photos
   ├── Wedding Photo 01
   ├── Wedding Photo 02
   └── Wedding Photo 03
```

Later:

```text
Category
   ↓
Wedding
   ↓
Projects
   ├── Rahul & Priya Wedding
   └── Sharma Wedding
```

This gives the final website a consistent structure.

# 6. Category Entity

Create:

```text
categories
```

Recommended schema:

| Field           | Type      | Required |
| --------------- | --------- | -------: |
| id              | UUID      |      Yes |
| name            | VARCHAR   |      Yes |
| slug            | VARCHAR   |      Yes |
| description     | TEXT      |       No |
| cover_image_url | TEXT      |       No |
| is_active       | BOOLEAN   |      Yes |
| is_visible      | BOOLEAN   |      Yes |
| sort_order      | INTEGER   |      Yes |
| created_at      | TIMESTAMP |      Yes |
| updated_at      | TIMESTAMP |      Yes |

# 7. Field Responsibilities

### `id`

Unique category identifier.

Use UUID.

### `name`

Display name:

```text
Wedding Photography
```

### `slug`

URL-friendly identifier:

```text
wedding-photography
```

### `description`

Optional short description.

Example:

```text
Elegant wedding stories captured with a cinematic approach.
```

### `cover_image_url`

Optional category cover image.

This becomes useful later for the public category pages.

### `is_active`

Controls whether the category can be used within CMS operations.

### `is_visible`

Controls whether the category appears publicly.

### `sort_order`

Controls category ordering.

### timestamps

Track creation and modification.

---

# 8. Active vs Visible

Keep these concepts separate.

### Active

Determines whether the photographer can currently use the category.

### Visible

Determines whether visitors can see the category.

Example:

```text
Category: Wedding

Active: YES
Visible: YES
```

Public:

```text
Wedding
```

Another example:

```text
Category: Old Portfolio

Active: NO
Visible: NO
```

It remains in the database but isn't displayed publicly.

Required.

* Trim whitespace
* Reasonable maximum length

# 20. Delete Category

Deletion requires special handling because categories will eventually be connected to photos and projects.

Do **not** blindly delete a category that is already referenced.

Example:

```text
Wedding
   ↓
42 Photos
   ↓
Cannot safely delete
```

Instead:

> This category is currently used by 42 photos. Deactivate it instead, or remove its associations first.

This protects data integrity.

---

# 21. Category Delete Strategy

Recommended behavior:

### Category has no associated content

Allow deletion after confirmation.

### Category has associated photos/projects

Prevent hard deletion.

Offer:

```text
Deactivate Category
```

This is much safer for a commercial CMS.

# 23. Activate / Deactivate

Quick action:

```text

```

When deactivated:

* It remains in database
* Existing content isn't deleted
* It shouldn't be selectable for new content where appropriate
* Public visibility should be disabled or respected according to business rules

Recommended rule:

```text
is_active = false
```

should automatically prevent public display even if `is_visible` accidentally remains true.

# 53. Business Rules

### BR-CAT-001

Category names must be unique.

### BR-CAT-002

Category slugs must be unique.

### BR-CAT-003

Inactive categories cannot be used for new content where category selection is required.

### BR-CAT-004

Hidden categories must not appear on the public website.

### BR-CAT-005

Categories referenced by content cannot be hard-deleted.

### BR-CAT-006

Category deletion must not cascade-delete photos or projects.

### BR-CAT-007

Category ordering must be persisted.

### BR-CAT-008

Only authenticated administrators can manage categories.

### BR-CAT-009

Every important category mutation should create an activity log.

### BR-CAT-010

Public APIs must return only public-safe category information.

# 54. Edge Cases

### EC-01 — Duplicate name

```text
Wedding
```

already exists.

**Expected:** Reject.

### EC-02 — Duplicate slug

```text
wedding
```

already exists.

**Expected:** Reject.

### EC-03 — Delete category in use

**Expected:** Block deletion.

### EC-04 — Category inactive

**Expected:** It remains available for historical content but isn't selectable for new content.

### EC-05 — Hidden category

**Expected:** Not shown publicly.

### EC-06 — Empty database

**Expected:** Proper empty state.

### EC-07 — Long description

**Expected:** Validation prevents exceeding maximum length.

### EC-08 — Invalid cover image

**Expected:** Upload rejected.

### EC-09 — Failed image upload

**Expected:** Category isn't left in a broken state.

### EC-10 — Reorder failure

**Expected:** UI reverts or refreshes to persisted order.

### EC-11 — Two simultaneous edits

**Expected:** Backend remains authoritative and returns an appropriate conflict/error when necessary.

# 64. Security Requirements

* [ ] All admin category APIs require authentication.
* [ ] Validate all input server-side.
* [ ] Sanitize user-generated text where necessary.
* [ ] Validate uploaded file type and size.
* [ ] Don't expose storage secrets.
* [ ] Don't allow client-side manipulation of protected fields.
* [ ] Don't allow category deletion to cascade into content deletion.
* [ ] Log important mutations.

---

# 65. Performance Requirements

The category system should remain fast even with hundreds of categories.

Use:

```text
pagination
indexed search
database sorting
database filtering
```

Don't load thousands of unrelated records just to display the first page.

For a typical photography business, the category count will likely be small, but the architecture should still be clean.
